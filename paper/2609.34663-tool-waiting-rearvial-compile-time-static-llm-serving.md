# Tool Waiting and Re-arrival in Compile-Time-Static LLM Serving: Cost Mechanisms and Configuration Selection

> **arXiv:** [2609.34663](https://arxiv.org/abs/2609.34663)  
> **Authors:** Dongkyeom Jang, In-Nea Wang, Junho Jeong  
> **Published:** September 28, 2026

---

## I. Introduction

Agentic LLM 서비스에서는 모델이 외부 툴(API, 계산기, DB 등)을 호출하고 결과를 기다린 뒤 추론을 재개하는 사이클이 반복된다. 이 tool waiting 구간 동안 세션의 KV cache는 가속기 메모리에 idle 상태로 머문다. 이 사이에 다른 요청이 슬롯을 소진하면 KV cache가 evict되고, re-arrival 시 비용이 큰 re-prefill을 다시 수행해야 한다.

이 문제는 **compile-time-static serving substrate**(NPU 등 특수 하드웨어)에서 더욱 심화된다. 이러한 환경은 최대 처리량을 위해 아래 파라미터들을 컴파일 시점에 고정하기 때문이다:

- **Batch bucket set** — 시퀀스 길이를 그룹화하는 이산 경계값 집합
- **Maximum batch size** ($B_{\max}$) — 동시 처리 가능한 최대 배치 크기
- **KV cache slot 수** — 할당된 KV cache slot의 고정 개수

이 논문은 tool waiting과 re-arrival이 이 rigid한 compile-time 제약과 어떻게 충돌하는지 분석하고, 비용 메커니즘을 규명한 뒤, simulation 기반의 최적 구성 선택 방법을 제안한다.

## II. Execution Structure and Measurement Environment

### 대상 환경

- 하드웨어: **Rebellions RBLN-CA25 서버** (8 cards / 32 devices)
- NPU 기반 statically compiled serving — batch bucket set, $B_{\max}$, KV cache slot이 모두 컴파일 시점에 고정
- 파라미터 변경 시 **재컴파일 필요** (약 7~8분 소요)

### 측정 방식

- 성능 지표로 wall-clock time이나 단순 utilization 대신 **device time**을 사용하여 실제 compute 및 실행 비용을 정확히 측정
- Tool waiting time 분포는 실제 agentic 프레임워크(코딩 어시스턴트 등)의 트레이스 데이터에서 도출한 경험적 분포를 사용
- 기준(baseline) 구성: bucket set `{1, 2, 4, 8}`, $B_{\max} = 8$, KV cache slot 8개

## III. Cost Mechanisms of Tool Waiting and Re-arrival

Re-arrival 시 발생하는 실행 비용을 세 가지 메커니즘으로 분해한다.

### 1. Discrete Batch Alignment

Static 엔진은 고정된 bucket set을 사용하므로, re-arriving 세션의 토큰 길이가 미리 정의된 bucket 경계에 맞지 않으면 구조적 비효율이 생긴다.

> **패딩 역설:** 동시성 6, 특정 bucket 크기가 bucket set에 없는 구성에서, 툴 대기 **없을 때** vs. **있을 때(re-arrival 발생)** 를 비교하면:
>
> | | 툴 대기 없을 때 | 툴 대기 있을 때 |
> |---|---|---|
> | Padding 비율 | 0.235 | **0.120** (↓ 좋아 보임) |
> | Decode 실행 시간 | 기준 | **1.51배 증가** (↑ 실제론 나빠짐) |
>
> Re-arrival 세션의 토큰이 짧아지면서 padding은 줄지만, 불규칙한 재진입 타이밍이 배치를 작게 쪼개거나 prefill interference를 유발해 실제 실행 비용은 오히려 증가한다. **Padding 비율은 한 배치 내 낭비 토큰만 반영할 뿐, 배치가 얼마나 자주·작게 실행되는지를 포착하지 못한다.**

### 2. KV Cache Survival

Re-arriving 세션이 이전에 계산해둔 KV cache slot을 재사용할 수 있는지 여부가 end-to-end 지연에 결정적인 영향을 미친다.

- Slot 수가 부족하면 tool waiting 구간 동안 새로 들어온 요청이 FIFO 방식으로 기존 slot을 evict
- Eviction 발생 시 → re-arrival 때 비용이 큰 full re-prefill 수행

### 3. Prefill Interference

갑작스러운 re-arrival이 현재 진행 중인 다른 요청의 decode 또는 prefill 단계와 충돌하면 병목이 생긴다. Static 배치 제약이 엄격할수록 이 간섭의 영향이 커진다.

## IV. Simulator Design and Validation

### IV-A. Time-Order Replay Simulator

구성 파라미터가 바뀌면 스케줄링 다이나믹과 re-arrival 타이밍 자체가 변하므로, 단순 분석적 모델만으로는 평가가 불가능하다. 이를 위해 커스텀 **time-ordered replay simulator**를 개발하여 각 구성 하에서의 요청 처리 타임라인을 정확히 재현한다.

### IV-B. Assumptions and Scope

- 단일 LLM 인스턴스 대상
- 세션당 단일 tool call (multi-turn은 범위 외)
- 합성 워크로드 사용 (prompt 길이, generation 길이를 통제)

### IV-C. Comparison Metrics and Validation Design

- 주요 지표: **device time** (실제 실행 비용 반영)
- Simulator 예측값과 실제 하드웨어 측정값을 비교하여 정확도 검증

### IV-D. Execution Pattern Reproduction and Cost Prediction

Simulator는 구성별로 실행 패턴(batch 구성, KV cache eviction 여부, prefill interference)을 재현하고 실행 비용을 예측한다.

### IV-E. Direction and Interpretation of Prediction Residuals

예측 잔차의 방향성과 해석을 분석하여 simulator의 신뢰 범위를 명확히 한다.

## V. Selection of Compile-Time Configurations and Cost Improvement

### V-A. Comparing Configuration Candidates with the Simulator

후보 구성 **2,077개**를 simulator로 전수 평가하여 최적 구성을 선택하고, 미확인 새 입력에 대해 검증.

### V-B. Gains from More KV Slots and a Changed Bucket Grid

| 시나리오 (동시성 8, KV 재사용률 낮음) | 비용 절감률 |
|---|---|
| $B_{\max}$ 단독 확대 | **8.25%** |
| 최적 구성 (batch size + bucket set 조정) | **9.72%** |

KV cache slot을 늘리고 bucket grid를 조정하면, tool waiting 중 eviction으로 인한 re-prefill 비용을 크게 줄일 수 있다.

### V-C. Priority of Configuration Changes by Reuse Loss

최적화의 효과는 **KV reuse loss 비율**에 따라 달라진다. Reuse loss가 클수록 slot 증가·bucket 조정의 효과가 크고, 이미 reuse가 잘 되는 환경에서는 우선순위가 낮다.

### V-D. Conditions under Which the Gain from Additional KV Slots Is Limited

KV 재사용률이 이미 높은 경우(예: 18회 중 17회 reuse 성공), 구성 변경으로 인한 개선 효과는 **0.59%** 수준에 그쳤다. Workload의 KV cache 패턴을 사전에 파악하는 것이 중요하다.

### V-E. Compile Cost and Memory Usage

- 구성 변경 시 재컴파일 비용: 약 **7~8분**
- Bucket grid 확장 및 KV slot 증가는 가속기의 static memory 사용량 증가로 이어지므로, 성능 개선과 메모리 상한선 사이의 trade-off를 고려해야 함
- 논문은 offline compile 비용과 online 실행 비용을 별도로 취급하며, 이를 하나의 break-even으로 합산하지 않음

### V-F. Application Procedure and Scope

Simulator 기반 구성 선택은 production 하드웨어에서의 trial-and-error 없이 최적 구성을 찾을 수 있는 실용적인 접근법이다.

## VI. Limitations and Conclusion

### VI-A. Limitations

1. **Workload scope:** 세션당 단일 tool call만 평가. Multi-turn agentic 워크플로우, 반복적인 re-arrival 체인은 범위 외
2. **System scope:** Rebellions RBLN-CA25 특정 환경 기반. 다른 벤더 가속기(GPU/TPU 등)나 다른 attention 구현체에서도 동일하게 나타나는지는 미검증
3. **Measurement & modeling:** 최적화 루프는 discrete simulation 기반이며, 일부 tail-risk 지표($\kappa_{1\%}$ 등)는 비용 함수 정의에 의존
4. **Reproducibility:** Cache eviction 귀책 로그, tolerance sensitivity 등 세부 사항은 복잡한 비동기 tool-waiting 상호작용으로 인해 supplementary material에 위임

### VI-B. Conclusion

- Compile-time-static 환경에서 tool waiting과 re-arrival은 고정된 batch 구조·KV slot 한계와 충돌하며 기존 static 가정을 무너뜨린다
- Padding 비율 같은 단일 지표에 의존하는 튜닝은 역설적으로 성능을 악화시킬 수 있다
- 최적 구성 선택은 **KV reuse loss와 re-arrival 패턴을 중심으로 한 진단**에 기반해야 한다
- **Future work:** Tool-waiting 다이나믹을 반영한 compile-time 구성 선택 파이프라인 자동화, multi-tool/multi-turn 환경으로의 확장, 이기종 하드웨어 검증

## 용어 정리

| 용어 | 설명 |
|---|---|
| **Compile-Time-Static Serving** | Batch 크기, bucket set, KV cache slot을 컴파일 시점에 고정하는 서빙 방식 |
| **Bucket Set** | 시퀀스 길이를 이산 그룹으로 묶는 경계값 집합. 예: `{1, 2, 4, 8}` |
| **KV Cache Slot** | Attention key-value 계산 결과를 저장하는 캐시 공간 |
| **Re-arrival** | 외부 툴 실행 완료 후 추론 엔진으로 돌아오는 세션 재진입 이벤트 |
| **Reuse Loss** | Re-arrival 시 KV cache가 evict되어 재사용에 실패하는 경우 |
| **Prefill Interference** | Re-arrival 요청의 prefill이 기존 진행 중인 decode와 경합하는 현상 |
| **Device Time** | 가속기 실제 실행 비용을 반영한 측정 지표 (wall-clock time과 구별) |
